# 笔记「同步 / 新建 / 保存」重新设计方案

日期：2026-11-16
状态：已按方案 B 实现（含第 7 节三项与 4.8 的规则变化），Go 与前端回归通过，尚未在真实服务器上走查。标「已验证」的问题用临时测试在假远端上复现过，现已改成 `internal/notes/sync_failure_test.go` 里的回归测试；其余是读代码得出。

与方案的出入：
- 问题清单入口放在侧栏底部「回收站」同一行（「N 项未同步」），不是同步按钮上的角标：顶部工具行在最窄宽度下放不下第六个按钮。手机档是同一个弹出清单，没有另做二级页。
- 没有做「丢弃」：从未上传的记录进回收站后不再上传（4.8），也就不会再失败，不需要这个入口。
- 「暂时无法同步」按连续失败 3 次显示，不按分钟数。
- 拉取失败（服务器上的文件下载不下来）只记在内存里，重启后重试一次；上传失败落库。

## 1. 现状流程

### 1.1 一条笔记的一生

| 步骤 | 发生了什么 | 落在哪 |
| --- | --- | --- |
| 新建 | 本机立刻建「未命名.md」，状态 `pending`，唤醒同步 | `notes.Create` |
| 输入 | 停 0.5 秒写入本机库（带版本号比对），状态 `pending`，每次保存都唤醒同步 | `use-note-document.ts` → `notes.Update` |
| 同步轮 | 唤醒后等 0.75 秒；另有每分钟一次定时。整轮上限 2 分钟 | `desktop/notes.go` `runNotes` |
| 拉取 | 取**整个网盘**的 FileNode 快照，逐个比对 Notes 下的节点，变了的下载正文 | `syncVault` / `pull` |
| 上传 | 待同步项按「目录 → 附件 → 修改时间从旧到新」排序，每轮最多 12 条；每条：读远端 → 上传正文 → 带 `ifInState` 写 FileNode | `push` / `SetFileConditional` |

### 1.2 状态

持久化的是 `status`（`pending` / `synced` / `conflict` / `remote_deleted`）加两个开关：`deleted`（在回收站）、`uncertain`（新建请求发出后没收到结果）。

界面只认得其中一部分：

| 界面显示 | 对应 |
| --- | --- |
| 未保存 | 编辑器里有还没写进本机的输入 |
| 待同步 | `pending`（**包括**排队中、反复失败、被别的记录挡住、`uncertain`，看不出区别） |
| 已同步 | `synced` |
| 存在版本冲突（可点开对比） | `conflict` |
| 远端文件已删除，本地副本仍保留 | `remote_deleted` |
| 保存失败 +「另存为恢复笔记」 | 写本机失败或版本号对不上（后台刚拉了新版而你正在输入） |

同步失败没有落到具体记录上：整个库只有一个 `vault.error` 字符串，原样显示在正文区顶部，不管当前打开的是哪篇。

## 2. 问题清单

| # | 问题 | 后果 | 依据 |
| --- | --- | --- | --- |
| 1 | **一条失败，整轮终止**。拉取或上传任意一条报错，`syncVault` 直接返回；排序是固定的，所以同一条每轮都排在前面 | 它后面的所有记录永远传不上去。这次的毒记录就是这样拖住整个库的 | 已验证 |
| 2 | **新建时请求超时是死路**。记录被标 `uncertain`，之后每轮都报 2208：服务器没写入时不敢重发；服务器写入了时按 blobId 认领，而 Stalwart 落库后会换 blobId，认不上 | 永久卡住并触发问题 1。界面不显示 `uncertain`，移动 / 删除 / 对比都被拒，没有任何入口能解开 | 已验证（两种情况） |
| 3 | **附件闸门过宽**。库里只要有一个附件不是 `synced`（远端被删、冲突、与这篇无关的都算），所有笔记都不上传，且不报错 | 全库静默停止上传；同时「还有待同步项」为真，后台每 0.75 秒空跑一轮，每轮一次全网盘快照 | 已验证 |
| 4 | **错误不指向具体记录**，红字挂在当前打开的笔记上方 | 用户以为是眼前这篇出了问题 | 界面代码 |
| 5 | **文案不可读且对不上原因**。库级错误原样显示英文码；映射表里 2207 写的是「请检查笔记 MCP 设置与账号权限」，而它实际还代表「服务器不接受这次写入」；2202 同时代表真冲突、网盘里别的文件刚好变了、取快照时有变化三件事 | 提示误导排查方向 | 界面代码 |
| 6 | **账号级 state 竞争被报成冲突**。`ifInState` 是整个网盘的版本号，模板同步、AI 设置同步、文件模块上传都会让它变 | 偶发红字「2202 note_conflict」，下一轮自己好，但没有任何笔记真的冲突 | 已验证 |
| 7 | **不分暂时与永久，也不退避**。断网、服务器拒绝一视同仁，每分钟加每次编辑各重试一次 | 永久性错误无限重试；每次重试都是全网盘快照 | 调度代码 |
| 8 | **「立即同步」可能什么都没做**。后台正在跑时手动同步直接返回成功 | 按钮转一下就停，用户以为同步完了 | `Sync` 的 `TryLock` |
| 9 | **输入时同步过密**。保存 0.5 秒 + 同步 0.75 秒，持续输入约每 1.3 秒一整轮（快照、读远端、上传、写、刷新网盘缓存、再读） | 请求多；也放大了问题 6 的竞争窗口 | 调度代码 |
| 10 | 拉取同样会整轮终止：Notes 里有一个超过 4MB 的 `.md` 或某个正文下载失败，之后的都不拉也不传 | 同问题 1 | 读代码 |
| 11 | 只改名 / 移动 / 删除也会把正文重新上传一遍 | 多余流量，不影响正确性 | 读代码 |
| 12 | 整轮 2 分钟硬超时，超时若正好落在写请求上就变成问题 2 | 大库首次同步、传大附件时可能触发 | 读代码 |

冲突判定本身（基线节点 + 正文摘要 + `ifInState` 条件写、两台设备同名新建的合并、对比与解决）没有发现问题，也有测试覆盖。问题集中在**调度**（谁先谁后、失败了怎么办）和**反馈**（告诉用户什么）。

## 3. 局部修补 vs 重构

| | A 局部修补 | B 重写同步循环（推荐） | C 改成操作队列 |
| --- | --- | --- | --- |
| 做法 | 在现有循环里把 `return err` 改成继续，修掉 2、3，改文案 | 数据模型与冲突判定不动；重写「一轮同步怎么走、失败怎么记、何时重试」，每条记录自带同步结果，界面按记录提示 | 按原设计文档建 `note_operations` 表，每次改动是一条可重放的操作 |
| 解决 | 1、2、3、5 | 全部 12 项 | 全部，另外能精确表达「先改名再编辑」这类顺序 |
| 没解决 | 4、6、7、8（错误仍是库级一条，仍不分类） | — | — |
| 风险 | 低，但错误仍无处安放，下次换一种毒记录还是看不出是谁 | 中：同步循环与界面状态要重测；本机库只加字段，旧版程序能照常读 | 高：现有本机数据要迁移，两台设备的测试全部重写，而用户能感知的改进与 B 相同 |

推荐 B。现在的模型是「每条记录保存期望的最终样子，同步负责把远端追平」，对笔记够用，问题不在模型而在循环；C 换来的顺序精度当前没有场景需要。

## 4. 新设计（方案 B）

### 4.1 每条记录自带同步结果

`Entry` 增加四个字段（只加不改，旧版本忽略）：失败类别、服务器原话（只在详情里显示）、连续失败次数、下次重试时间。`status` 的取值不变。

用户看到的状态收敛为六个：

| 状态 | 含义 | 能做什么 |
| --- | --- | --- |
| 未保存 | 输入还没写进本机 | 等 0.5 秒或 Ctrl+S |
| 待同步 | 已在本机，排队或正在核对（含原来的 `uncertain`） | 无需操作 |
| 已同步 | 与服务器一致 | — |
| 暂时无法同步 | 网络或服务器暂时的问题，会自动重试 | 可手动重试 |
| 同步失败 | 服务器明确不接受，自动重试没有意义 | 看原因、重试、（回收站里从未上传的）丢弃 |
| 存在冲突 / 远端已删除 | 不变 | 对比并选择 |

### 4.2 一轮同步逐条隔离

- 只有整轮性的问题才终止整轮：离线、未登录、取快照失败、Notes 根目录不见了。记在库上，界面显示为不带红色的「离线，联网后自动同步」这类状态。
- 单条的拉取或上传失败记在那一条上，继续处理下一条。
- 上级文件夹还没上传成功的子项本轮跳过，不算失败；清单里只报那个文件夹。
- 每轮 12 条的上限只计真正发了请求的，被跳过的不占名额。

### 4.3 错误分类与重试

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| state 竞争 | 网盘里别的文件刚好变了 | 当轮内重新读取再写，最多 3 次；不显示、不计失败 |
| 暂时性 | 超时、断线、5xx | 按条退避（5 秒、30 秒、2 分钟、10 分钟封顶）；连续失败超过几分钟才显示「暂时无法同步」 |
| 永久性 | 服务器拒绝属性、无权限、超配额、文件过大、本机附件文件丢失 | 标「同步失败」，停止自动重试；内容再次修改、用户点重试、程序升级后首次启动时各重置一次 |
| 真冲突 | 远端这条记录本身变了 | 走现有冲突流程，不变 |

错误码：2207 只保留「没有写权限」，新增 2209「服务器不接受这次写入」；state 竞争改用内部错误，不再借用 2202。

### 4.4 结果不明的请求自己核对

写请求没收到结果时，下一轮先核对再决定，不再是终态：

- 新建：按「上级目录 + 名称」找远端节点。找到且**正文内容**一致（下载比对，不比 blobId）就认领；找到但内容不同，走现有的「两边同名」流程；没找到说明没写入，重新创建。
- 更新：读远端这条。内容等于本机就算成功；等于旧基线就重发；其它情况是冲突。

### 4.5 附件闸门收窄

笔记只等**还在正常排队**的附件（它们排在笔记前面、同一轮就会传）。失败、冲突、远端已删除的附件不再挡任何笔记。

### 4.6 调度

- 保存到本机仍是 0.5 秒；因编辑触发的上传改为停止输入约 3 秒后，或切换笔记 / 离开模块时立即触发。新建后马上改名通常只产生一次远端写入。
- 去掉「还有待同步项就立刻再跑」：只有本轮确实传成功了至少一条、且还有可传的才立刻续跑，否则等定时或退避到点。
- 整轮 2 分钟硬超时改为按条超时。
- 「立即同步」等正在进行的那轮结束后再完整跑一轮，结束时提示结果：「已同步」或「3 项未能同步」。

### 4.7 界面

- 去掉正文顶部那条库级红字。
- 标题栏的状态只说当前这篇：失败时可点，弹出原因（人话）、「重试」与可展开的技术详情（数字码 + 服务器原话）。
- 目录树：失败的条目标红点，冲突仍是 `!`，待同步仍是 `•`。
- 同步按钮带问题数角标，点开是「未能同步的项目」清单：名称、所在目录、原因、重试 / 打开；点一行跳到那一条。手机档同一入口进二级页。
- 「保存失败」的文案分开：写本机失败说磁盘；版本对不上说「这篇笔记刚从其他设备更新，你的输入还没保存」，按钮仍是另存为恢复笔记。

文案对照（详情里保留数字码）：

| 情况 | 现在 | 改为 |
| --- | --- | --- |
| 服务器不接受写入 | 2207 note_write_forbidden: invalidProperties: Invalid property. (type) | 服务器不接受这篇笔记的写入，内容仍保存在本机 |
| 结果不明 | 2208 note_remote_result_uncertain | 不显示，状态为「待同步」，下一轮自动核对 |
| state 竞争 | 2202 note_conflict | 不显示 |
| 离线 / 连不上 | 2205 notes_unavailable | 离线，联网后自动同步 |
| 超过大小或配额 | 2203 note_invalid_input | 文件超过服务器的大小上限 / 网盘空间不足 |

### 4.8 一条规则变化

新建后还没上传就被移进回收站的记录，不再上传到服务器的 `.czl-trash`：它只留在本机回收站，恢复后才开始同步。少一类写入，这次的毒记录也属于这一类。代价是其它设备的回收站里看不到它。

## 6. 风险

- 按名称认领结果不明的新建：同名不同内容走冲突流程，两份都保留，不会丢。
- 永久失败不再自动重试：服务器修好后要靠升级 / 修改 / 手动重试触发。升级后首次启动统一重置一次，现有卡住的记录会自然解开。
- 逐条隔离后顺序不再严格，但每条仍是「读远端 → 条件写」，冲突判定不依赖顺序。
- 上传防抖从 0.75 秒变 3 秒：另一台设备看到改动会晚两三秒。
- 状态显示改动较多，需要在真实服务器上走一遍新建、断网、冲突、回收站。

## 7. 可以后做的三项

不影响上面的方案，可以同一批做，也可以放后面：

1. 只改名 / 移动 / 删除时不重传正文（问题 11）。
2. 输入时后台拉到新版：自动转成该笔记的冲突（本机 = 你的输入，远端 = 新版），不再停掉自动保存让用户手动另存。
3. 每分钟的对账从「全网盘快照」改为 `FileNode/changes` 增量，全量只在增量失效时做。
